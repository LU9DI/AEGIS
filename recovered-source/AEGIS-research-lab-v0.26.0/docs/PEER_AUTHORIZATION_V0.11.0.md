# Peer authorization protocol — MALEBOLGE v0.11.0

## Purpose

This stage closes a specific v0.10 gap: a relay-to-relay link must not accept a peer based only on a self-asserted identity key. A peer now sends an authority-certified descriptor in the link-authentication hello, and signs the complete transcript including that descriptor.

## Hello format

All fields use network byte order where a length is present:

| Field | Size | Meaning |
|---|---:|---|
| `LINK_HELLO` | 1 byte | Message discriminator |
| mode | 1 byte | `0` anonymous client, `1` relay peer |
| target relay ID | 20 bytes | Binds the hello to the receiving relay |
| peer relay ID | 20 bytes | All-zero only for client mode |
| peer Ed25519 public key | 32 bytes | All-zero only for client mode |
| nonce | 32 bytes | Per-hello freshness challenge generated by initiator |
| certificate length | 2 bytes | Length of the following descriptor JSON |
| certificate | 0–16,384 bytes | Canonical JSON with relay signature and authority signature; required in strict relay mode |
| signature | 64 bytes | Ed25519 over the domain-separated unsigned hello for relay mode; all-zero for client mode |

The initiator signature covers the target ID, peer identity fields, nonce, certificate length and exact certificate bytes. The responder then signs the full hello plus its own identity digest. The initiating client can remain unidentified in mode `0`; it does not attach a relay descriptor or persistent client identity.

## Receiver decision sequence

1. Enforce overall hello size and exact certificate-length consistency.
2. Check that the hello names this relay as target.
3. Verify the claimed peer ID derives from the supplied public key.
4. Verify the initiator's signature over the complete hello.
5. In strict mode, reject an absent certificate; parse strict JSON and call `DirectoryVerifier.verify_peer_descriptor`.
6. Verify the descriptor's identity key and relay ID exactly match the signed hello fields.
7. Apply optional `authorized_peer_ids` policy.
8. Claim the peer+nonce replay token, then reply with the responder's target-bound signature.

`verify_peer_descriptor` fails closed without a fresh authority-signed revocation snapshot. It applies descriptor lifetime, relay signature, authority certification, revocation, and descriptor-sequence rollback checks. Persistent trust state is required by `configure_directory_authorization`.

## Configuration and boundaries

A relay must have an identity private key and a currently authority-certified descriptor that matches its identity digest, onion key, loopback endpoint and listener port. Configure the verifier with a pinned authority key, persistent `state_path`, and fresh signed revocation snapshot first. Then call:

```python
relay.configure_directory_authorization(
    verifier,
    signed_descriptor,
    authorized_peer_ids={known_peer_id_bytes},  # optional stricter policy
)
```

When `authorized_peer_ids` is absent, any valid currently directory-authorized relay can be a peer. Configure an allowlist when deployment policy requires a narrower peer set.

## What this proves and does not prove

It improves authorization and freshness checks at the relay link. It does not provide transport confidentiality, hide identities from neighboring relays, establish a global directory consensus, provide external monotonic anti-rollback, persist replay tokens, or prove anonymity against traffic analysis. The lab's endpoint validation remains literal IPv4 loopback. The hello includes certificate bytes and thus increases setup traffic; no WAN claim is made. The custom protocol integration has not received independent cryptographic review.

Low-level unit-test fixtures with no configured `DirectoryVerifier` can still exercise the older key-possession-only relay mode. This compatibility path is not an authorization boundary and must not be used for production network listeners.
